# 08 · 设计决策记录

> **状态**：设计稿（持续修订）· 相关：[02-architecture](./02-architecture.md) · [06-roadmap](./06-roadmap.md)
> **本文回答**：哪些关键设计已经定下？决定的理由与影响是什么？
>
> 格式：`D0XX | 日期 | 决策 | 理由 | 影响`。新决策**追加**在末尾，不修改历史条目。

## D001 | 2026-10-27 | 三层架构：基础层 / 兼容层 / 应用层

**决策**：系统分为 L1 基础层（机制）、L2 兼容层（生态翻译）、L3 应用层（插件），层间只向下依赖。
**理由**：把"机制"与"生态特例"分离后，新增生态不应改动底层；分层让扩展成本可预测。
**影响**：L1 代码中不得出现生态专名；跨层调用只走能力注册表。

## D002 | 2026-10-27 | 能力注册表是唯一的扩展点

**决策**：宿主能力统一为 `capability id → {参数, 权限, handler}`，注册/鉴权/路由/审计集中在注册表。
**理由**：分散的 if/match 会让"加一个能力"变成多处改动，扩展成本随能力数线性上升。
**影响**：新增能力 = 注册一条 +（对外暴露时）映射表加一行；核心逻辑不再出现业务分支。

## D003 | 2026-10-27 | 能力 id 命名空间 + 权限四级

**决策**：能力 id 形如 `<域>.<动作>`（`clipboard.write` 等）；权限分 `read / write / exec / dangerous`。
**理由**：统一命名让映射表可读、权限可按前缀批量推导；四级足够表达风险差异且便于默认策略。
**影响**：能力目录与权限判定都基于 id 前缀，插件按能力粒度授权。

## D004 | 2026-10-27 | 清单新增 4 个可选字段

**决策**：`apiVersion` / `origin` / `capabilities` / `permissions` 全部可选，旧插件行为不变。
**理由**：需要版本协商、来源分档、声明式需求、显式提权；但不能让存量插件失效。
**影响**：解析器向后兼容；`origin` 以宿主判定为准，清单声明仅作提示。

## D005 | 2026-10-27 | 兼容层独立成层，且只有一个真源

**决策**：生态适配器（方言 + API 映射 + 生命周期）独立成层；能力映射表是唯一真源，由它生成 SDK 表面、宿主路由与注入脚本。
**理由**：同一份生态 API 语义在手写多处的形态下必然漂移，扩展成本与缺陷率都上升。
**影响**：新增一个生态 API = 改一行表 + 重新生成；需要引入代码生成步骤与"生成物 == 真源"测试。

## D006 | 2026-10-27 | 兼容结论必须显式呈现

**决策**：兼容分级结论（可运行 / 缺哪些能力 / 不兼容原因）必须在插件中心与安装流程中展示。
**理由**：静默失败（装得上但功能不可用）是最难排查、也最伤信任的失败模式。
**影响**：兼容判定需产出结构化结论；插件中心的展示与结论模型绑定。

## D007 | 2026-10-27 | 插件页面走本地回环 HTTP，不用 file://

**决策**：插件资源由宿主以 `http://127.0.0.1:<port>/<token>/…` 提供。
**理由**：WebView2 不允许在 http 源内嵌 `file://` 帧，`file://` 方案会导致插件白屏。
**影响**：需要资源服务（token 前缀 + 目录穿越防护 + 注入点），插件不得假设独占 origin。

## D008 | 2026-10-27 | 文档只描述目标设计

**决策**：`docs/` 只写目标形态与决策，不写历史流水与实现现状；差距以里程碑范围的形式记在规划文档里。
**理由**：设计阶段的文档要能回答"要做成什么样"，历史与现状由 git 承载，避免文档腐化。
**影响**：文档随设计演进重写是常态；每份文档带状态头与交叉引用。

## D009 | 2026-10-27 | 兼容层先做通用机制，再接首个生态

**决策**：先把兼容层机制（接口、映射表、生成、判定）落地并做稳，再接一个具体生态验证。
**理由**：先接生态会把生态特例渗进机制层，返工成本高。
**影响**：M3 与 M4 分离；具体生态的适配设计在 M4 阶段另文产出。

## D010 | 2026-10-27 | Windows 优先，不引 UI 组件库

**决策**：当前只做 Windows；主面板手写 CSS，不引入 UI 组件库与 CSS 框架。
**理由**：目标生态与主流用户集中在 Windows；主面板交互极简，组件库带来的体积与风格成本不划算。
**影响**：平台相关能力（应用索引、图标、快捷方式）需要按 Windows API 单独实现，跨平台需后续评估。

## D011 | 2026-10-27 | 注册表数据模型在核心 crate，执行体在宿主壳

**决策**：能力注册表的类型、权限模型与策略判定放在纯 Rust 核心 crate（零 Tauri 依赖），具体能力实现（需要 Tauri 运行时）注册在宿主壳的启动阶段。
**理由**：核心 crate 必须能脱离 Tauri 单测；能力实现又必然依赖窗口、剪贴板、文件系统等宿主能力。
**影响**：新增能力 = 在宿主壳注册一条 handler；策略与判定逻辑始终可单测。

## D012 | 2026-10-27 | 生态调用面收口到能力注册表

**决策**：生态 SDK（当前为 `window.rubick.*`）不再直连底层插件，而是翻译成能力调用，统一经注册表鉴权与执行。
**理由**：直连底层会绕过权限判定，且每加一个生态 API 都要改多处实现。
**影响**：生态 API 与能力之间存在一层显式映射；映射表是该生态适配设计的一部分。

## D013 | 2026-10-27 | 授权确认随清单能力一起落地

**决策**：`Prompt` 档在授权 UI 与授权记录就绪前按拒绝处理。
**理由**：没有确认界面的"稍后再说"就是默默放行，宁可先拒绝并给出可读错误。
**影响**：来源未知的第三方插件暂时拿不到写类能力；授权 UI 落地后同一处策略即可放行。

## D014 | 2026-10-27 | 宿主 API 先在宿主窗口提供

**决策**：`window.mytools.*` 先在宿主窗口可用；插件页面的注入与桥接随生态适配层一起做。
**理由**：能力注册表与鉴权先在宿主侧跑通，再把同一套协议注入插件页面，避免两套实现。
**影响**：插件在适配层落地前仍使用生态 SDK 调用能力（已收口到同一注册表）。

## D015 | 2026-10-27 | 来源按 provenance 判定，不按清单内容

**决策**：插件的 `origin` 由宿主按**来源**决定——装在用户插件目录里的一律 `custom`，`ecosystem` 只由生态适配器在安装时赋予，`official` 只赋予产品自带插件；清单里的 `origin` 字段只能把来源**收紧**为 `custom`。
**理由**：来源直接决定默认权限（写类能力是否需要确认）。若按清单字段判定，任何插件加一行 `"pluginType": "ui"` 就能给自己提权，等于把授权模型作废。
**影响**：生态适配器（M3/M4）与官方插件体系（M5）需要负责"赋予来源"，这是它们的验收项之一。

## D016 | 2026-10-27 | 需要确认的能力走"拒绝 + 记录 + 重试"

**决策**：策略判定为需要确认且没有授权记录时，宿主返回 `CAPABILITY_DENIED` + `consentRequired`，由前端弹窗询问；允许则写入授权记录并重试一次，拒绝则以明确错误结束。
**理由**：确认框必须由界面呈现，而能力调用发生在异步链上；"先拒绝、拿到同意再重试"能让同一条调用路径同时覆盖允许与拒绝两种结果。
**影响**：授权记录按插件 + 能力粒度持久化，可在设置中逐条撤销；撤销后下次调用重新询问。

## D017 | 2026-10-28 | 映射表是生态能力的唯一真源

**决策**：每个生态的能力映射写成 `mappings/<ecosystem>.json`（JSON，避免给核心 crate 增加新依赖），后端路由、生成的 SDK 表面与参数整形全部由它派生；生成物提交入库，并用逐字节一致性测试锁死。
**理由**：同一份映射若手写多份（后端 match、前端 shim、文档），新增能力必然漂移；把"加一个能力"压缩成"注册一条 + 表里加一行"才能真正降低扩展成本。
**影响**：改映射后必须重跑 `cargo run -p mytools-compat --bin gen_compat_sdk`；一致性测试会拦住忘记重跑的情况。

## D018 | 2026-10-28 | 方言识别与来源判定分离

**决策**：插件"用什么清单方言写"由清单内容识别（如 Rubick 的 `pluginName` / `pluginType`），但它只决定**用哪个适配器评分**，不改变 `origin`；`origin` 仍只由 provenance 决定（D015）。
**理由**：兼容分级需要知道方言，而权限分级只能看来源。两者混用会让插件通过写几个字段既冒充生态插件又获得更宽的默认权限。
**影响**：`LoadedPlugin` 同时携带 `ecosystem`（方言）与 `origin`（来源）；插件中心的兼容徽标来自前者，权限判定只读后者。

## D019 | 2026-10-28 | 兼容矩阵排除 preload、双口径报率（已被 D020 取代）

**决策**：静态扫描不读取 `preload.js` 的 API 引用与原生标记，只记录“是否自带 preload”；矩阵同时输出“全部插件 Tier 1 率”与“无原生依赖插件 Tier 1 率”。
**理由**：preload 运行在 Node/Electron 上下文，把它引用的 `require` 算进宿主缺失项会误判所有带 preload 的插件；但 preload 本身又确实代表运行时风险。拆成“扫描口径”和“展示维度”比直接忽略更诚实。单一总数会掩盖原生插件占比，双口径才能看出纯 Web 子集的真实覆盖。
**影响**：矩阵不把 preload 直接降级；Tier 1 目标按双口径分别跟踪，禁止只报好看的口径。

## D020 | 2026-10-29 | 放弃外部生态兼容，工具改为自研独立插件包

**决策**：删除 L2 兼容层（`mytools-compat` crate、映射表、生成 SDK、方言识别）、插件市场与兼容性分级、npm 生态安装通道；工具一律以**独立第三方插件包**（目录 + 清单 + 页面，自包含、无构建步骤）交付，放在仓库 `独立插件仓库`，由用户经「插件中心 → 开发者 → 安装本地目录/压缩包」安装。所有插件均独立分发。
**理由**：Rubick 生态的插件普遍硬依赖 Electron（preload 里的 Node 内置模块与 npm 依赖），WebView 宿主无法承载；实测「可安装但跑不起来」的样例让兼容矩阵产生假阳性（Tier 1 实为不可运行）。与其做不可靠的兼容层，不如把工具按宿主能力重写——反正最终都要自己维护。工具不进二进制还能让宿主体积与升级面更小。
**影响**：生态适配相关代码与文档删除；已安装的生态插件在迁移中自动清理；插件中心去掉商店与分级，只剩「已安装 / 开发者 / 偏好设置」。

## D021 | 2026-10-29 | 能力权限向自装插件放开，真实文件走目录授权

**决策**：`clipboard.read` / `clipboard.history` 取消「仅官方可用」并升为 `exec`（自装插件首次调用弹确认），`clipboard.remove` 取消「仅官方」限制，`fs.write` 由 `dangerous` 降为 `write`；自装插件访问真实文件必须先 `fs.pickdirectory`（系统对话框）取得**目录授权**，授权记录持久化且可在设置中撤销。
**理由**：工具以第三方插件形态交付，若沿用「危险能力一律拒绝自装插件」，文件类工具（批量重命名、本地搜索）根本无法落地。把"能不能碰真实文件"交给**用户显式选目录**这一动作，比按来源一刀切更贴近真实风险模型：目录是用户点的、授权可撤销、越界路径仍然拒绝。写类能力降级后，安全性由路径边界（插件沙箱 ∪ 已授权目录）而非权限档位兜底。
**影响**：能力目录新增 `clipboard.history` / `clipboard.remove` / `fs.pickdirectory` / `fs.grants` / `fs.revokegrant`；新增 `directory-grants.json`；设置页新增「目录授权」区。

## D022 | 2026-10-29 | 插件商店保留为「工具目录」，rubick 插件只作实现参照

**决策**：插件中心保留**插件商店**分区，但它的条目不是外部生态包，而是**我们自己的工具清单**（`src/data/toolCatalog.ts`）：每条记录一个工具（名称、说明、分类、状态、能力需求、功能点、将来的 npm 坐标），并挂一个 `reference` 字段——对应 rubick 插件的包名、npm 链接与 logo，作为**实现时的界面与功能参照**。商店不做兼容分级、不做安装前预检；状态为「可安装」的工具走本地目录安装（将来改走 npm）。
**理由**：D020 清退了生态兼容，商店若继续装 rubick 包会给用户「装得上但跑不起来」的假象；但把商店整个删掉又丢掉了工具的**发现与进度视图**——用户需要知道有哪些工具、哪些已可用、哪些在做。工具既然最终都由我们自己维护，条目就应该是我们的工具，rubick 只作为设计参照留在条目里。
**影响**：插件中心侧栏 = 插件商店 / 已安装 / 开发者 / 偏好设置；工具按「先读参考插件再重写」的顺序推进（顺序见 [06-roadmap](./06-roadmap.md) M7 工具进度表）；参考链接只用于开发，不构成运行时依赖。

## D023 | 2026-10-29 | 能力 id 必须全小写，且注册即校验

**决策**：能力 id 一律 `<域>.<动作>` 全小写（`system.netinterfaces`、`fs.pickdirectory`、`fs.revokegrant`），并在注册入口显式校验：`validate_capability_id` 不通过或 id 不在 `CAPABILITY_IDS` 常量表内时**记 error 日志并跳过注册**，同时由单测锁住 id 形态与新能力在册。
**理由**：注册表会拒绝含大写字母的 id，而旧的注册辅助函数只打日志不报错——能力于是**静默不存在**，插件侧只看到 "unknown capability"，排查成本极高（本轮 `system.netInterfaces` / `fs.pickDirectory` / `fs.revokeGrant` 三个能力就是这样丢失的）。id 形态属于对外契约，必须有单一真源与守卫。
**影响**：`commands/capability.rs` 维护 `CAPABILITY_IDS`；新增能力时先改清单再注册，插件清单里的 `capabilities` 也要用同形态的小写 id。


## D024 | 2026-10-30 | 宿主按职责组织，能力注册失败中止初始化

**决策**：保留 L1/L2 产品边界；宿主内部明确启动装配、IPC、运行时、业务服务、平台设施和纯 Rust 核心的职责。能力实现按领域注册，注册表作为运行时能力集真源；不再维护与实际注册重复的 `CAPABILITY_IDS` 白名单。非法 ID 或重复注册向启动入口返回错误。本项替代 D023 中“维护白名单并跳过错误注册”的做法，保留 ID 全小写的约束。

**理由**：IPC 与领域实现混合使扩展影响面持续增加，重复白名单不能证明实际能力已注册。领域注册返回错误可直接暴露初始化缺陷；同步系统操作通过有并发上限的后台执行器，避免阻塞异步执行线程。

**影响**：新增能力在对应领域模块声明 ID、权限和处理器，并补充相关测试与规范；插件身份和启用状态在执行前校验。前端由运行时统一负责挂载清理，授权请求排队且随插件实例销毁取消。插件包 API 与 IPC 命令名称保持稳定。


## D025 | 2026-10-30 | 共用业务服务不反向依赖 IPC

**决策**：应用索引、启动目标解析、搜索合并、设置与剪贴板访问由服务层拥有；IPC 和插件能力都消费服务。Windows 图标提取、剪贴板后台采集放在平台设施中。服务、运行时和平台设施禁止引用 `commands` 或声明 IPC 命令，由架构测试持续约束。

**理由**：从能力 handler 调回 IPC 模块，会把传输接口变成实际业务依赖，阻碍复用和测试。统一业务入口和状态所有权，可以避免前端命令与插件能力出现不同实现；搜索使用单份插件快照，避免并发刷新时元数据不一致。

**影响**：原有 IPC 命令名、参数、返回格式和插件能力 ID 保持稳定。应用扫描、图标提取与搜索的阻塞工作在后台执行；桌面窗口、托盘与快捷键命令保留 Tauri 交互适配职责。

## D026 | 2026-10-31 | 参考交互重写工具，离线包保持独立

**决策**：以 Rubick 插件的交互工作流为参考，按 MyTools 宿主能力重写工具；不执行参考插件的 Electron preload，不复制无明确许可的代码或图标。公共样式、工具函数和离线依赖由源码真源同步到各包，安装后没有跨目录依赖；只有既定 JSON 官方包随宿主播种。

**理由**：界面与功能接近参考，不需要恢复已经终止的生态兼容层。独立资源保持分发和升级边界清楚，离线依赖避免 CDN 故障影响工具启动。

**影响**：文件搜索限制在授权目录，批量重命名先整批验证且不覆盖目标；危险操作仍需授权。JSON 路径过滤不执行脚本，Markdown 清洗预览 HTML，正则测试在有超时的 Worker 中运行。OCR 使用用户自己的 WebAPI 凭据。完整交互目标与平台差异见 [12-tool-interactions](./12-tool-interactions.md)。

## D027 | 2026-10-31 | 文件搜索使用 Everything，交互尽量贴近参考插件

**决策**：以用户指定的 uTools 文件搜索、批量重命名，以及 Rubick 超级 Markdown 为交互基准。全盘搜索走 Everything Unicode IPC（Query2），不以目录遍历替代索引搜索；Markdown 复用同系列开源编辑器。新增文件选择与系统保存能力，保留明确授权与执行确认。

**理由**：自行简化的界面和工作流增加切换成本。文件搜索的索引速度与查询语法属于核心功能；原生文件选择、逐项预览和撤销属于批量重命名的基础交互。

**影响**：`fs.globalsearch` 与内容预览分别为 exec 权限；预览限制在当前查询结果。`fs.pickfiles` 明确授权所选条目所在目录，`fs.exporttext` 只写系统保存对话框选择的位置。原有授权目录搜索保留供局部导入使用。本项替代工具交互规范中“默认搜索只做目录遍历”的限制，文件写入授权边界不变。

## D028 | 2026-11-02 | 原生拖放与中键快捷面板

**决策**：文件拖入由宿主记录原生窗口事件，插件只能消费当前窗口的短期一次性记录，不能提交任意路径换取授权；切换插件会话时丢弃旧记录。中键面板作为宿主快捷入口，以独立窗口展示，系统鼠标监听只负责触发，插件启动仍经过既有运行时。

**理由**：浏览器 File API 不可靠地提供 Windows 文件夹路径，也不能证明真实拖放来源。面板不应干扰主窗尺寸、插件会话或复制一套插件执行机制。

**影响**：新增 fs.importdropped 和 onFilesDropped；保留显式能力授权与目录边界。中键开关持久化，关闭后不吞中键；面板失焦隐藏、屏幕边界内定位，入口本地持久化。

## D029 | 2026-11-02 | Windows 动态子窗口文件接收

**决策**：在 UI 线程维护本应用窗口及 WebView2 子窗口的 OLE IDropTarget；动态枚举并补充接收器，清理已销毁窗口的对象。只接受 CF_HDROP，导入通知沿用按窗口隔离的一次性记录。

**理由**：WebView2 浏览器默认拖放被关闭时，接收依赖原生子窗口注册；仅在启动时注册不能覆盖运行中新增的子窗口。系统显示禁止拖入发生在插件回调之前，不能仅通过修改桥接事件解决。

**影响**：保持 COPY 反馈，拖入本身不移动文件；系统路径仍经能力与目录授权确认。我的面板保留 HTML 拖动排序，不安装原生文件接收器。

## D030 | 2026-11-03 | 面板上下文由宿主统一交付

**决策**：唤出面板时由宿主捕获资源管理器选择与剪贴板上下文，选择插件后绑定到目标窗口及插件身份，通过声明并授权的 `context.read` 一次性获取所需类型，120 秒过期。不通过生命周期广播实际数据。

**理由**：面板获得焦点后无法可靠恢复之前的选择；插件各自监听和模拟复制会产生冲突。统一来源适配、内存快照及受控交付能保持插件独立，并复用现有会话和权限边界。

**影响**：重命名接收选中文件，OCR 仅预载截图，真实文件修改及外部识别继续由用户执行。搜索框沿用 `hostSearch` 协议；插件中心嵌入时复用顶部输入，独立窗口使用页面内输入。[上下文规范](./13-launch-context.md) 定义数据格式、限制及扩展方式。
