> **M3 / M4 / M6 终止说明**：Rubick 生态高度依赖 Electron（preload + Node 模块 + 主进程能力），
> 在 WebView 宿主中无法可靠承载，兼容矩阵实测 Tier 1 兼容率 40%、且预检会把「preload 依赖 Node」的
> 插件误判为兼容。战略上放弃「兼容外部生态」，改为**自研工具包**路线：宿主只提供插件平台与能力，
> 工具一律独立交付（见 M7）。相关代码、商店与分级机制已清退。

### M1 · 基础层：能力注册表 ✅

**目标**：把"能力"从散落的分支收进一张注册表，宿主只认 `capability id`。

**范围**

- 核心 crate 新增 `capability` 模块：`Capability{id, permission, handler}`、`CapabilityRegistry`、`CallContext`、`Policy`、错误类型（扁平序列化 `code` / `message` / `capability`）
- 权限策略 `Policy`：`read/write/exec/dangerous` 四档 + `Allow/Prompt/Deny`
- 前端 `window.mytools.*`：`call(capability, args)` + 生命周期 + `getEnv()` + 版本协商
- 调用上下文：插件 id、来源、窗口 label，供策略判定与审计

**验收**

- [x] 已实现的能力全部注册，各有单测
- [x] 鉴权路径（未知能力 / 参数非法 / 权限不足）各有单测
- [ ] 能力调用开销 < 5ms（基准待建立）

### M2 · 清单 v1 与来源分档 ✅

**目标**：插件能声明需求，宿主能按来源授权。

**范围**

- 清单解析新增 4 个可选字段（向后兼容）
- `origin` 由宿主按**来源**判定（不按清单内容），清单声明只能收紧
- 插件中心显示来源标记、不兼容原因、声明的能力
- 授权记录持久化（插件 + 能力粒度），设置页可查看与撤销
- 授权确认流程：需要确认 → 弹窗 → 允许后记录并重试

**验收**

- [x] 无新字段的旧插件照常安装运行
- [x] 声明版本高于宿主的插件在加载时标记为不兼容并给出原因
- [x] 未声明的能力调用被拒（`CAPABILITY_DENIED` + 能力 id）
- [x] 授权确认闭环：确认 → 记录 → 重试成功；拒绝 → 明确错误；撤销 → 重新询问

### M3 · 兼容层通用框架 ⛔ 终止

**终止原因**：兼容层服务于「接入外部生态」，而生态路线本身已被放弃（M4 终止）。
保留 L2 会留下一整套没有真实消费者的机制（映射表、生成器、分级判定），反而增加维护面。
相关 crate（`mytools-compat`）、生成 SDK、映射表与分级 UI 已全部删除。

### M4 · 首个生态适配 ⛔ 终止

**终止原因**：Rubick 插件普遍依赖 Electron 运行时与 preload 的 Node 模块；宿主是纯 WebView，
无法承载。实测「可安装但跑不起来」的样例（`ip-config-rubick-plugin`）依赖
`public-ip` / `internal-ip` / `node-navigator` / `canvas-confetti` 等 npm 模块与 `os` 内置模块。

**保留结论**：能力映射表与生成器的**思想**（单一真源）已并入 M7 的工具包规范；
生态专有内容（字段映射、API 清单、兼容矩阵）不再产出。

### M5 · 官方插件体系 🚧

**目标**：宿主能力成为插件（含第三方工具）可用的一等能力。

**范围**

- 系统能力（剪贴板、应用索引、窗口、托盘、网络、文件）以能力开放
- 官方插件包：目录 + 清单 + 版本 + 播种 + 升级
- 官方来源策略：read/write/exec 免确认，dangerous 仍需确认

**交付**

- [x] `clipboard.read` / `clipboard.history` / `clipboard.remove`、`app.list`、`app.launch`
- [x] `net.fetch`（HTTP(S)，Exec 权限）、`system.notify`（Write）、`fs.read` / `fs.write`
- [x] `app.launch` 复用启动器目标解析（AUMID / 文件 / URI）
- [x] 官方插件包编译进二进制 + 启动播种 + `official` provenance（`mytools-hello`、`mytools-json`）
- [x] 插件 iframe 内的 `window.mytools.call()` 直连能力注册表（按插件 scope 授权）
- [x] 插件中心安装列表新增「打开」入口
- [ ] 其余工具以**独立第三方插件包**交付（见 M7）

### M6 · 生态接入闭环 ⛔ 终止

**终止原因**：插件市场与兼容性预检都服务于生态接入。生态清退后，商店没有内容源，
「兼容分级 / 显示模式」失去意义且会误导用户（预检把 preload 依赖 Node 的插件判为兼容）。
商店、预检、Tier 徽标与显示模式已全部删除；插件中心改为「已安装 / 开发者 / 偏好设置」。

### M7 · 工具包体系 🚧

**目标**：工具以**独立第三方插件**交付——不进应用二进制，用户自行安装；宿主只提供平台与能力。

**范围**

- 工具包形态：目录 + `plugin.json` + `index.html`，自包含、无构建步骤
- 能力目录补齐（剪贴板历史、目录授权等）
- 目录授权模型：用户用系统对话框选目录 → 授权记录 → 插件在该目录内读写
- 插件中心改造：删除商店与分级；开发者区保留本地目录 / 压缩包 / npm 安装
- 工具清单与开发指南（[10-plugins-and-tools](./10-plugins-and-tools.md)）

**交付**

- [x] 工具包目录规范与开发指南（`tools/README.md` + docs/10）
- [x] 目录授权机制：`fs.pickdirectory` / `fs.grants` / `fs.revokegrant` + 设置页目录授权区
- [x] 能力权限口径放开给自装插件（clipboard.read/history/remove 取消"仅官方"；`fs.write` 由 dangerous 降为 write）
- [x] 生态清退：兼容层 / 商店 / 预检 / 分级 / 显示模式删除，生态插件目录自动清理
- [x] **插件商店 = 工具目录**：`src/data/toolCatalog.ts` 收录 11 个工具（状态：内置 / 可安装 / 开发中），
      每条挂 rubick 参考插件（包名 + npm 链接）作为界面与功能参考；已实现的走本地目录安装，
      将来改走 npm；不恢复兼容分级与预检
- [x] 首批工具包：计算稿纸、Markdown 编辑器、系统剪贴板、ipconfig（`system.netinterfaces`）、颜色助手
- [x] 取色器、本地搜索、文件批量重命名、Ctool、讯飞 OCR 独立包与所需宿主能力
- [x] 按参考插件重构全部工具的核心交互，独立页面 / 脚本 / 样式和离线依赖；范围见 [12-tool-interactions](./12-tool-interactions.md)
- [x] 插件实机加载、核心数据转换、目录选择与授权拒绝、危险操作确认门禁
- [x] 三项优先修复：Everything IPC、文件 / 文件夹选择与预览、同系列 Markdown 编辑器与笔记管理
- [x] 搜索与重命名经用户同意临时授权后的真实操作验收；结束后撤销新增授权

### M8 · 宿主职责重构 ✅

**目标**：保持两层产品架构与插件 API，将启动装配、IPC、运行会话、能力实现和前端壳职责分离。

**范围与验收**

- [x] 启动逻辑按存储、插件平台、桌面集成分组，入口只负责装配
- [x] 能力按领域注册，IPC 不含业务 handler；注册错误明确阻止不完整的平台启动
- [x] 运行会话独立管理；能力执行走有并发上限的阻塞线程池，并在执行前校验身份
- [x] 前端壳初始化、授权交互、插件错误与运行生命周期各有明确归属
- [x] 授权请求排队，视图与事件订阅在销毁时清理
- [x] 自动回归：前后端测试、类型检查、lint 和生产构建通过
- [x] 实机验收：主窗口、插件能力与越权拒绝、授权与取消、分离窗口、托盘设置事件及悬浮球开关
- [x] CDP 调试端口自动分配与发现，不依赖固定端口
- [x] 共享业务服务化：应用索引与启动、搜索、设置、剪贴板及系统目录由服务层提供；图标与后台采集归平台设施；依赖边界由测试约束

## 3. 暂缓项

| 项 | 原因 | 重新评估条件 |
|---|---|---|
| 插件签名与信任链 | 当前靠能力声明 + 权限拦截 | 工具生态达到需要防投毒阶段 |
| 插件资源隔离（超时/内存） | 同进程模型暂无隔离手段 | 出现实际稳定性问题 |
| 工具包在线目录 | 工具目前靠本地安装分发 | 工具数量超过人工分发能力 |
| 多端同步 | 非当前瓶颈 | 稳定后 |
| macOS / Linux | 平台特性差异大 | 单独立项 |

## 5. 进度同步约定

1. **每完成一个里程碑**：更新本文档 §1 状态列 → 更新对应专题文档 → 在 [08-design-decisions](./08-design-decisions.md) 追加相关设计决策。
2. **状态取值**：`✅ done` / `🚧 进行中` / `⬜ 未开始` / `⛔ 终止`（终止必须写原因）。
3. **完成定义**：里程碑内的勾选项全部打勾才算 done；部分完成保持 `🚧` 并在状态列注明剩余项。
4. **文档与代码同 PR**：规范/架构类改动必须与实现同 PR，或紧随其后（禁止滞后超过一个里程碑）。
5. **数字口径**：测试数量、耗时等易变数据只写进 `AGENTS.md` 与提交记录，不进本文档。
