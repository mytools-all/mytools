# 01 · 需求分析

> **状态**：设计稿（持续修订）· 相关：[02-architecture](./02-architecture.md) · [06-roadmap](./06-roadmap.md)
> **本文回答**：为谁做、要解决什么、做到什么程度算成功、什么不做？

## 1. 背景与机会

| 现状 | 痛点 |
|---|---|
| **Rubick**（Electron）插件生态最丰富 | 安装包 ~100MB，常驻 100-300MB，启动 1-3s |
| **uTools** 交互优秀 | 免费版限制插件数量，重度用户被迫付费；插件仅在官方市场分发 |
| **Wox / Alfred** 等启动器 | 跨平台能力弱，生态局限于本地小工具 |

**机会**：用 **Tauri 2**（Rust + 系统 WebView）做一款"启动器 + 插件化工具箱"——安装包 < 15MB、
常驻 < 80MB、启动 < 500ms，并把**常用工具自己重写成插件**。

> **路线变更**：早期目标是"兼容 Rubick 生态"。实测发现 Rubick 插件普遍硬依赖 Electron
> （preload 里的 Node 内置模块与 npm 依赖、主进程能力），WebView 宿主无法承载，
> 兼容层投入产出比极低（D020）。因此改为**自研工具包**路线：宿主提供插件平台与能力，
> 工具以独立插件包交付。

## 2. 目标用户与场景

| 类型 | 占比 | 关注点 |
|---|---|---|
| **开发者** | 60% | 工具启动、格式转换、剪贴板、终端入口、调试 |
| **效率达人 / 知识工作者** | 30% | 翻译、计算、单位换算、OCR、配色、Markdown |
| **重度定制用户** | 10% | 装第三方插件、写自己的插件、脚本化工作流 |

典型场景

1. 唤起启动器 → 搜到工具 → 直接用（计算稿纸、剪贴板历史、Markdown、JSON）
2. 装一个工具包 → 装上即用；需要真实文件时弹目录选择框授权
3. 自己写工具 → 按规范声明能力 → 与官方工具同一运行时

## 3. 目标与成功判据

**核心目标**：做一款**轻量、可靠、工具够用**的启动器 + 插件化工具箱；工具以插件形态交付，
新增工具不需要重编宿主。

| 维度 | 目标 | 判据（可度量） |
|---|---|---|
| **工具供给** | 常用工具齐备且即装即用 | 规划工具 100% 以插件包交付；装上即用，无需改宿主 |
| **扩展** | 新增能力 / 新增工具的成本恒定 | 加一个能力 = 注册一条；加一个工具 = 一个插件目录 |
| **分层** | 职责清晰、依赖单向 | L1 不含插件专名；跨层只走能力注册表 |
| **安全** | 插件碰不到不该碰的东西 | 越权调用被拒且可解释；真实文件访问需用户选目录授权 |
| **性能** | 保持轻量优势 | 冷启动 < 800ms；空载常驻 < 80MB；插件扫描 < 50ms |

**非目标**：兼容外部生态、复刻生态的深度能力、做通用插件平台、跨平台。

## 4. 功能需求

### 4.1 基础层（机制）

| 需求 | 说明 | 优先级 |
|---|---|---|
| 能力注册表 | 能力 = id + 参数 + 权限 + handler；注册/鉴权/路由/审计集中一处 | P0 |
| 清单规范 v1 | 统一 `Manifest` + `apiVersion` + `capabilities` + `permissions` | P0 |
| 运行时载体 | iframe 宿主 + 独立窗口 | P1 |
| 权限策略 | 按来源与权限级别判定；用户可授权与撤销 | P0 |
| 契约版本 | `apiVersion` 协商；不兼容显式报错 | P0 |
| 资源服务 | 回环 HTTP + token + 目录穿越防护 | P0 |
| 错误总线 | 插件崩溃可采集、去噪、展示 | P0 |
| 目录授权 | 用户选目录 → 授权记录 → 插件在该目录内可读写 | P1 |

### 4.2 应用层

| 需求 | 说明 | 优先级 |
|---|---|---|
| 官方插件 | 维护者独立发布的插件，使用普通安装通道 | P1 |
| 工具包 | 独立第三方插件包：目录 + 清单 + 页面，自包含、无构建步骤 | P0 |
| 插件中心 | 已安装 + 开发者两视图；启用/停用/卸载/打开目录 | P0 |
| 安装通道 | 本地目录 / 压缩包 / npm 包 | P0 |
| 能力目录 | 覆盖常用系统能力（剪贴板、文件、网络、通知、应用索引） | P0 |

## 5. 非功能需求

| 维度 | 指标 |
|---|---|
| 安装包体积 | Windows MSI < 15MB |
| 内存常驻 | < 80MB（空载） |
| 冷启动到可输入 | < 800ms |
| 热启动 | < 500ms |
| 搜索首屏 | < 100ms |
| 插件目录扫描 | < 50ms |
| 单插件激活 | < 300ms |
| 能力调用开销 | < 5ms（本地能力） |
| 稳定性 | 单插件崩溃不影响宿主 |
| 平台 | Windows 优先；其它平台不在当前范围 |

## 6. 范围外

- macOS / Linux 支持
- 外部生态兼容（Rubick 等 Electron 生态）
- 平台深度能力（主进程级系统能力、任意进程执行）
- 通用插件平台（市场运营、多端分发、插件签名信任链）
- AI 集成、移动端

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 自研工具的工作量与维护成本高于预期 | 高 | 工具按优先级分批；每个工具自包含、互不影响 |
| 权限模型引入额外弹窗打扰用户 | 中 | 默认策略按来源分档；只读能力免打扰；授权可撤销 |
| 插件供应链风险（任意来源的包） | 中 | 清单校验 + 能力声明 + 权限拦截 + 来源标记 + 目录授权 |
| 能力目录扩张导致策略复杂 | 中 | 能力按权限四档归类，目录授权单独承载文件类风险 |
| 文档与实现脱节 | 中 | 状态头 + 里程碑验收标准与实现一一对应 |
